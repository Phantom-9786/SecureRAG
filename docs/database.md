# Database design

Tables: roles, permissions, categories, role_permissions, role_category_access, users,
documents, chunks, conversations, messages, message_sources.

Users reference one role. Grants join roles to categories and permissions. Documents reference
categories and uploaders. Chunks reference documents. Conversations reference owners; messages
reference conversations. Message sources link answers to retrieved chunks with source numbers.

UUIDs are generated by Python; timestamps are timezone-aware and default to database now().
Emails must be lowercase/trimmed and unique. User activity and token_version support later revocation.
Initial embeddings use vector(1536). No approximate vector index is installed: V1 ranks an explicitly
authorized subset with exact cosine distance. Foreign key and history ordering indexes are included.

Documents default inactive and processing. Later ingestion marks ready only after all chunks are saved.
PDF bytes belong to private file storage; only storage_key and filename are stored in PostgreSQL.
Document/chunk deletion is restricted where references exist; V1 uses document deactivation.
Deleting a conversation cascades messages and source mappings, without deleting source documents.

The initial migration contains an immutable SQL snapshot. Future schema changes require a new Alembic
revision. Do not edit an applied migration. `updated_at` changes when a Conversation is updated through
SQLAlchemy; the conversation service must explicitly touch it when appending a message.

Application traffic uses DATABASE_URL; Alembic requires DATABASE_URL_UNPOOLED. A development Neon branch
must be used before deploying changes to any production database. No remote database has been created
or modified by the Phase 1 scaffolding itself. Subsequently, on 2026-10-31, the authorized Neon
setup created a dedicated SecureRAG project and development branch and applied migration 0001.
See phase-1-validation.md for live verification results.
